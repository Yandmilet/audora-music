# 歌词匹配方案

给每首歌自动绑定一条尽量高质量、时间轴尽量精确的歌词。整体沿用音源匹配的思路（多路来源 → 硬过滤 → 内容校验 → 打分定档），但歌词有两个独有特点决定了方案形态：

1. **质量分层**：逐字轴 > 行级轴 > 均分近似轴，观感差异很大，不能混为一谈。
2. **错配比缺失更伤**：拿到另一首歌的歌词，比没有歌词更糟。所以宁可降级到均分近似，也不放宽匹配门禁。

参考实现对照：NeriPlayer（GPL-3.0，**只借鉴思路，不可抄代码**）。

---

## 一、质量分级（Tier）

| Tier | 内容 | 时间轴来源 | 可否 AUTO |
|------|------|-----------|-----------|
| **T1** | 逐字（真实字轴） | AMLL TTML（Apple Music 逐字，匿名可读）；规划中：酷狗 KRC | 是 |
| **T2** | 行级同步（LRC） | QQ `GetLyric`、网易云、本地 `.lrc`；规划中：LRCLIB | 是（过门禁后） |
| **T3** | 均分近似字轴 | 由 T2 行轴按「行时长 ÷ 字数」推算，UI 标「近似」 | 已是当前兜底 |
| **T4** | ASR 转写 | Whisper 转写已绑定音源 + LLM 清洗 | 否，只进 REVIEW |
| — | 无歌词 | 以上全 miss | 占位 |

> 关键约束：`LyricWord` 存 **UTF-16 code unit 字符数**而非文本片段（见 `lyric_word.dart`），整行文本是唯一真相源，天然杜绝「拼接后与原文对不上」，且中英混排/emoji 代理对不错位。逐行与逐字共用 `mappedLyricMs` 的 slope/offset 坐标系，校准逻辑不分叉。

## 二、当前已落地（T1 AMLL 链路 + T3 兜底）

数据链路：`AppState.loadLyricForCurrent` → `LibraryRepository.fetchLyric` →
`AmllTtmlProvider.fetchWordLyric`。AMLL 命中则**整条替换** LRC（含其自带译文，
自洽的一套，不与 QQ 行文本混拼），否则回落 LRC 并由 UI 层做均分近似。

### 匹配门禁（全部为可脱网单测的纯函数，在 `amll_ttml_provider.dart`）

```
① 按 QQ mid 精确查（qqSongMid 是曲库主键链路，命中即精确，零误配）
      ↓ 查不到
② 按标题查 → scoreAmllCandidate 过最低分 → 逐个候选拉正文校验
```

| 门禁 | 规则 | 作用 |
|------|------|------|
| 标题+歌手评分 | `titleScore(≤90) + artistScore(≤?)`，`< kAmllMinMatchScore(70)` 丢 | 拦标题近似但不同歌 |
| **歌手一票否决** | `artistScore < 30` 直接归零 | 标题再像、歌手对不上也丢（防串歌） |
| 最少行数 | `< kAmllMinLines(6)` 丢 | 防命中只有两行的碎片 |
| **字轴存在性** | `!hasWords` 丢 | 站点偶有只转整行的 TTML，无字轴不如本地均分 |
| **不对称时长容差** | 候选末行 vs 音频时长：偏短放宽到 `max(30s,15%)≤60s`，偏长收紧到 `max(12s,10%)≤30s` | outro/片尾静音让歌词早于曲尾是常态；偏长更可疑 |
| 文件名安全 | `isSafeTtmlFileName`：只收单个 `*.ttml`，拒 `/ \ .. 空白 控制字符` | 防被劫持响应路径穿越 |

候选上限 `kAmllMaxCandidates=4`（每个一次 raw 请求）。任何异常（超时/404/解析空）都不抛，逐字轴是体验增强不是播放前提。

### 均分兜底（T3）

`estimateWords` 按「行时长 ÷ 字数」补近似轴；为避免「每个字拖满整行到下一行的间隔」，行尾时间取下一行开始而非行自身时长末点。`wordsEstimated=true` 让 UI 在角落标「近似」——真实轴与均分轴观感差别大，不能让用户误以为是准的。

> 实测：热门歌 AMLL 命中率约一半（20 首中 11 首），命中 11/11 全带 `<span>` 字轴，零假阳性。

### 本机文件的取词入口（DB v12，2026-10-11）

歌词这条链路的入场券是 **songMid**：QQ 的 `GetLyric` 只认它，AMLL 的精确查也只认它。
本机文件（手机自带 / app 下载）天生没有，所以以前 `fetchLyric` 第一行
`if (id == null) return null` 就把它们全挡在外面——**播本地歌永远没词是写死的**。

现在走「先换身份，再取词」：

```
本机条目（标题+歌手+时长）→ metadata.resolveBatch 换回 songMid/albumMid
   → 缓存进 local_audio（离线也在）
   → fetchLyric(song, midFallback: songMid)   ← 曲库行没有可用 mid 时用它
   → 之后与在线歌完全同一条链路（QQ LRC → AMLL 逐字 → 均分兜底）
```

三条口径值得记住：

1. **`midFallback` 是备胎不是主路**。曲库行里有真 mid 时永远优先行内的，
   `local:` / `ref:` 这类派生键不算 mid（`LibraryRepository.midUsable`），
   因为它们喂给歌词接口只会换回 null。
2. **换不到身份就是没词**，不做「按文件名猜」的模糊取词——错配比缺失更伤（本文开头第 2 条）。
3. **播放时单补当前这一首**，不等整批补全轮到自己；补成功后 force 重取一次歌词，
   因为 `playQueue` 里那次是带着空 mid 跑的。

逐字层的渲染修正也记在这里：扫光行是自绘（`CustomPaint` + 两层 clip），
`TextAlign.center` 对**单行** `TextPainter` 不生效，导致「只有正在唱的这行偏左」。
补偿与推导见 `design-notes.md` §15 与 `lyric_layout_test.dart`。

## 三、四阶段流水线（对齐音源引擎，规划）

T2 多源接入后，把上面零散的门禁收敛成统一四阶段，复用 `match/` 的 `text_normalizer` / `title_parser` / `version_detector`：

```
Stage 1  候选召回：mid 直查 → 标题+歌手多源搜索（AMLL / QQ / 网易 / LRCLIB / 酷狗）
Stage 2  硬过滤  ：版本词黑名单（Live/现场/伴奏/instrumental/cover/翻自）+ 时长粗筛
Stage 3  内容校验：最少行数 + 字轴存在性 + 坍缩时间轴检测 + 乱码/编码检测 + 歌手一票否决
Stage 4  加权打分：标题歌手 / 来源质量(T1>T2>T3) / 时长吻合 / 文本规范度 → AUTO/REVIEW/放弃
```

**Stage 3 待补的校验**（借鉴 NeriPlayer，当前未实现）：

- **坍缩时间轴检测**：多行歌词但所有时间戳 `distinct < 2`（伪 LRC，全 `[00:00.00]`）——一招识破「假同步」。
- **乱码/编码检测**：GBK/UTF-8 错解导致的替换字符比例超阈值即丢。

**Stage 4 权重（草案，待 `probe_lyric.py` 实测后定档）**：

| 维度 | 权重 | 说明 |
|------|------|------|
| 标题歌手匹配 | 0.35 | 复用现有 S1；歌手对不上仍走硬否决 |
| 来源质量 | 0.25 | AMLL/KRC 逐字 > 官方行级 > LRCLIB > 本地 > ASR |
| 时长吻合 | 0.20 | 沿用不对称容差打分 |
| 文本规范度 | 0.20 | 校验层延伸：乱码率、占位符、重复行 |

置信度沿用 `0.82 / 0.62` 档位，但降级规则不同：T1 且 mid 直查可 AUTO；T4（ASR）产物一律 REVIEW，绝不 AUTO。

| 来源 | Tier | 价值 | 待验证 |

| **酷狗 KRC** | T1 | 第二逐字源，补 AMLL 未覆盖的一半；KRC 为固定异或密钥，社区已破解，含逐字轴 | 匿名可解率、字段结构 |

| 本地 `.lrc` / 嵌入标签 | T2 | 用户自带，最高优先 | 同名/sidecar 查找顺序 |

## 五、ASR 兜底（T4，规划）

仅 T1/T2 全 miss 时触发，音频直接用已绑定的 bilibili 音源流：

1. **转写**：faster-whisper 本地跑（large-v3，中文优先），出 segment 时间戳；兜底只求行级，不追逐字。
2. **LLM 清洗**（只清洗不生成，防幻觉）：删非歌词段（前奏哼唱/口白/`[Music]` 标记）、碎 segment 合并成行、以歌名/歌手/专辑作约束词典纠正同音字；严格限定「从转写文本中选择/合并/删除」，禁止补写没听到的词。
3. **产出**：标准 LRC + `origin: asr`，进 REVIEW，用户确认后固化为本地缓存。
4. **成本**：只对兜底触发；负结果缓存防重复转写；产物落盘（沿用图片磁盘缓存模式）。

> 待拍板：ASR 本地跑（faster-whisper，免费占机器）还是走 API（快但有成本），决定 T4 选型。

## 七、验证方式

延续 `probe_*.py` 实测文化：每接一个新源，先写脚本用曲库抽样 30~50 首验证**匿名命中率**与**假阳性率**，用数据定 Stage 4 权重与门禁阈值，尤其实测「标题模糊搜索」在各源的误配率（目前只有 AMLL mid 直查有实测数据）。P1 的门禁纯函数已有单测覆盖（`lyric_word_test` / `lyric_karaoke_test` / `lyric_mid_test` 等）。
