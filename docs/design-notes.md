# 设计要点

## 1. 界面语言

- 品牌色 `#E5484D`，中性灰底 `#F5F6F8`
- 大圆角（卡片 18px，胶囊 999px）
- 深色模式通过语义令牌整体切换

## 2. 音源状态徽章

| 徽章 | 含义 |
|------|------|
| 已匹配（绿） | ≥ 0.82 自动激活 |
| 待确认（橙） | 0.62 ~ 0.82，「我的 → 音源匹配管理」人工复核 |
| 无音源（灰） | 未找到候选 |

## 3. 空态优先于假数据

**库为空时显示空状态，不填 mock。** 早期版本塞 30 首假歌，后果是导入真歌后 UI 无变化，无法验证链路是否通了。契约：`repo == null`（单测/纯 UI 预览）才装 mock，真实运行时空库老老实实显示引导。

## 4. songMid 贯穿全链路

领域模型 `Song` 不含 `songMid`——它是播放器视角的「一首歌」。但 mid 会在边界丢失（搜索 → 入库 → 歌词），所以：

| 边界 | 承载类型 | 作用 |
|------|----------|------|
| 搜索 → UI | `ResolvedEntry` | 带着 mid 出 provider |
| UI → 入库 | `OnlineSong` | 类型层面强制拿到真实 mid |
| 本机文件 → 缓存 | `local_audio.song_mid` / `album_mid`（v12） | 文件天生没有 mid，换一次身份存下来；封面从 `album_mid` 派生，歌词从 `song_mid` 走 `fetchLyric(midFallback:)` |

教训：`importOnline(List<Song>)` 这种签名能编译能跑通，只是歌词永远空白。
同一个坑在本机歌曲上又长了一次：`fetchLyric` 早期第一行是 `if (id == null) return null`，
而扫描出来的文件在 `song` 表里根本没有行——「播本地歌永远看不到歌词」是写死在代码里的。

## 5. 收藏与播放统计独立建表

- `liked_song` / `play_log` / `play_stat` 不复用 `song` 的列——导入走 upsert，重导不应抹掉用户红心
- 收藏用 `INSERT OR IGNORE` 而非 `REPLACE`——`REPLACE` 会重置 `liked_at`，乱掉「最近收藏」排序
- 流水（play_log）与聚合（play_stat）分开——裁流水不影响统计

门限：满 30 秒才计数，只累计 0 < Δ ≤ 2 秒的位置增量。

## 6. 音质偏好是上限不是强制

用户选 192K → `qualityCeiling = 192K`。实际拉流：有就用，没有就拿最高可用档，绝不因「用户偏好的档位不存在」就放不出声。

两条上限各自独立（2026-10-11 拆分）：**在线音质**管拉流，**下载音质**管落盘。合在一条时做不到「在线听省点流量、下载留最好的」——而两者的代价本来就不一样：在线选高了只多花流量，下载选高了是把几十 MB 永久写进手机。所以改在线音质会立即换档并保住进度，改下载音质不碰正在播的这一次拉流。

「省流 64Kbps」档同时下线（B站 64K 实际是带强噪声的降级流）。历史存值映射到 132K 而不是落到「自动」——否则下线一个档就变成一次静默升档。

## 6.1 「猜你想听」为什么是我们自己拼的

QQ 音乐自己的个性化推荐接口匿名全部 `code=500003`（风控）：`music.personRec.*`、`musicTsRecommend.*`、`MUSIC.IndexTop.RecommendService`、`music.rec.*`、`music.musichallPlaylist.PlayListCgi`、`music.radio.UfoRadio` 等 11 个 module·method 组合实测一致，要 QQ 登录态，而本应用只有 B站扫码登录。

所以推荐算法放在应用侧，数据源仍全是 QQ 音乐，只用验证过可匿名访问的两类接口：歌手热歌（负责「像你的口味」）+ 热歌榜/新歌榜（负责「掺新的」）。口味来自本机统计：常听 2 票、收藏 1 票，取前两位歌手。这条前提由 `test/guess_for_you_test.dart` 用可覆写的假 provider 锁住。

## 7. 匹配速度 = 请求数决定

全局限流 30 次/分钟。Stage 2 预筛（enrichTopK=6）把详情请求从 30 降到 6，总请求 34→10，单首 ≈68 秒 → ≈20 秒。

两条护栏（`test/match_pipeline_test.dart` 锁死）：
1. 详情请求数必须被 `enrichTopK` 兜住
2. 预筛只能按打分排序，不能按播放量（翻唱/鬼畜热度高但不是真音源）

## 8. 按需匹配优先于批量预处理

这是投入产出比最高的优化：

```
原：导入 N 首 → 全部匹配完 → 才能播第一首    用户等 = 6~7 分钟
现：导入 N 首 → 点第 1 首 → 只匹配这一首      用户等 = ≈20 秒
```

配套细节：
- 队列必须就地替换对象（不替换的话播放页徽标一直显示「无音源」）
- 已有音源的歌必须短路（否则每次播放白烧配额）

## 9. 点播场景：宁播最相似候选，也不静默失败

AUTO 阈值 0.82 是批量预处理的标准（无人监督，宁缺勿滥）。但点播时大量新歌/冷门歌最高分卡在 0.81 左右，全部被标 REVIEW 不激活 → 用户点歌没反应。

分语境处理：

| 场景 | 激活策略 |
|------|----------|
| 批量预处理 | 只激活 AUTO（≥0.82） |
| 用户点播 | REVIEW 里 ≥0.60 的最高分候选也激活，toast 告知 |

红线：激活走事务内保证唯一性的 `BindingDao.activate`，0.60 底线以下不播。

## 10. 歌手筛选：显示真信息 vs 假装能筛

- 第一版接口不做筛选（参数被服务端忽略），就不摆筛选按钮，只把字段当标签显示
- 第二版接口真的有筛选（参数由服务端兑现），才配得上筛选按钮

三个判断：
- **「华语」必须自己合**：内地(200) + 港台(2)，周杰伦、陈奕迅全在港台档。只筛内地会让用户看不到周杰伦
- **分页终点是各档 total 之和**：服务端对越界页照样返回数据，多档合并时会把尾部混进其他档。必须按各档 total 主动截断
- **首字母是分区不是连续列表**：26 个字母分区拉取成本不可接受，交互只能是右侧竖直索引条

## 11. 关于限流与登录

- `-412` 是 IP 维度拦截，换 Cookie 换不掉
- 登录会放大风险（账号封禁），不是降低
- 登录收益是音质不是速度——搜索/匹配链路只用匿名指纹 Cookie（自动获取）
- 真正让「感觉慢」消失的是按需匹配，不是提高限流上限

## 12. 本机音乐：四条刻意的取舍（2026-10-11）

- **平台通道只能是插件，不能塞 `android/app`**。宿主 Activity 必须是
  audio_service 的 `AudioServiceActivity`（换成自定义 FlutterActivity 或其子类，
  引擎会 warm up 但 View 永不 attach —— 白屏，原因记在 AndroidManifest.xml 里）。
  插件通过 `ActivityAware` 拿当前 Activity，`GeneratedPluginRegistrant` 自动注册，
  app 侧零改动。
- **扫描用 MediaStore，SAF 只用来圈范围**。SAF 树遍历拿不到 ID3（歌手/专辑/
  时长），只会得到「01.mp3 未知歌手」；MediaStore 早解析好了。所以「本地目录」
  这项设置的语义是**扫描范围**（tree uri → 路径前缀过滤），不是「只读这个目录」。
- **下载不复用播放的解析路径**。`resolve()` 优先命中按在线音质挑的 URL 缓存并
  回写缓存，拿来下载会让「下载音质」变成摆设、还污染在线缓存；下载也绝不触发
  自动重匹配——重匹配后下到的会是另一场演出。故独立走 `resolveForDownload`。
- **不做断点续传，失败/取消一律删半成品**。DASH 直链约 100 分钟过期，续传要处理
  「旧链已失效但本地有半截文件」的组合，复杂度换不回收益；而半截文件留在下载
  目录里比没有更糟（列表里有、点开没声）。语义就是：清干净，重下从 0 开始。
- **已下载优先播本地**（用户选的语义），且换的是**队列里那一格**的 AudioSource
  而不是局部变量——只换局部变量会出现「实际播文件、播放页和通知栏显示 B站源」。

## 13. 两个目录为什么彻底分开

「本地」是扫描范围（只读语义），「下载」是写入位置。合成一个的话，用户把下载目录
设成 `/Music`，下次扫描就会把自己刚下的歌当成本机自带歌曲再收一遍，两批数据从此
分不清。落到实现上是：两个偏好键、两条 SAF 授权、`local_audio.kind` 二选一、
两个入口两张清单——任何一处合并都算回归。

## 14. 本机歌曲的真实封面与歌词：轻量补全，不进曲库（2026-10-11）

需求是「联网时本机歌和下载歌也要有真封面、播放时要有词；不联网用渐变占位」。
实现口径是**补全**，不是**入库**：

- **换到的身份只写进 `local_audio` 自己的三列**（`song_mid` / `album_mid` /
  `resolved_at`），**不给扫描条目在 `song` 表建行**。建行的代价是把本机歌混进
  曲库数字、播放统计和收藏——而「本机文件不做只活内存的假收藏」是已经拍板过的
  产品决定（见 `liked_source_of_truth_test.dart`）。清单隔开这条也是硬要求（§13）。
- **只存 mid，不存 URL**。封面 URL 是派生值（`QQSongMeta.coverUrlFor(albumMid)`），
  和 `song` 表同一口径；存 URL 等于在源换域名时把整库封面一起作废。图片本身
  已有磁盘缓存（`cached_network_image`），所以「离线也能看到上次拉到的图」不需要
  我们额外做什么。
- **不引 `connectivity_plus` 判网**。「不联网用渐变」由既有的 `CoverImage` 结构
  免费提供：渐变铺底 + 网络图盖在上面，加载中/拉不到都是 `SizedBox.shrink()`，
  底下那层自然露出来。补全侧不猜网络状态，改按**失败类型**分流：
  - 「三重校验不通过」= 这个源上确实没有这首歌 → 盖 `resolved_at`，冷却 3 天
  - 「请求异常」= 可能只是没网 → **什么都不标**，下次进页面还会试；连续 3 首
    就认定当前不在线并收手（分片边界生效，所以一片只有 6 首）
  代价是断网时进一次列表仍会撞最多 6 个请求，换掉的是「为一个布尔值加一条原生依赖」。
- **只有两个触发点**：进本机/下载列表时后台分片跑（postFrame，不阻塞，封面一首
  一首变真）；点开某本机首歌时若还没身份，**单补这一首**，补到了就 force 重取歌词。
  没有进度条、没有手动按钮——留下的口子记在 TECH_DEBT。
- **重扫绝不冲掉已缓存的身份**。`LocalAudioDao.upsert` 的 UPDATE 分支故意不写
  这三列：写进去的话每次扫描都会把用户攒下来的封面清空一遍。这条由
  `local_meta_sync_test.dart` 钉住。

## 15. 歌词页排版的三条决定（2026-10-11 真机反馈）

- **初始位置贴顶，不再垂直居中**。原来 ListView 上下各留 `0.3 × 屏高`，第 0 行
  歌词被顶到视口中线以下，前奏期看起来是「空半屏才下来」。改成不对称：
  `topPad = 8` / `bottomPad = 0.3 × 屏高`。于是唱前面几行时定位公式算出**负数**，
  被 `clamp(0)` 抬成 0 —— 这正是想要的行为：开局贴顶排布，唱过视口中线之后列表
  才开始往上滚。红线：定位计算（`_onState`）与列表内边距必须同源，漏掉 `topPad`
  会让当前行停在视口底部（真机出过）。
- **当前行的反差拉到 1.7 倍**：22pt / w800，其余 13pt / w500（原来 18 与 15 只差
  1.2 倍，等于没强调）。固定行高跟着涨：无译文 60→72、有译文 96→108——
  **行高余量必须按「高亮行折两行」算**（22×1.5×2=66），按普通行算就会压破下一句。
- **逐字（扫光）行必须自己补水平居中**，这是今天唯一的真 bug：
  `TextAlign.center` 对 **单行** `TextPainter` 段落**完全不生效**——实测
  `layout(maxWidth: 300)` 之后 `tp.width` 缩成文字本身的 54，
  `getOffsetForCaret(offset: 0).dx` 仍是 0，`paint(Offset.zero)` 就是贴左画。
  而普通行走的是 `Text`（RenderParagraph 会自己居中），所以现象是**只有正在唱的
  那一行偏左，其它行都是好的**——从界面上完全看不出这是两条渲染路径的差别。
  修法：画之前 `canvas.translate((盒宽 - 文字宽)/2, 0)`，位移作用在 dim/fill 两层
  之上，裁剪矩形保持在段落本地坐标系里，否则扫光边缘会跟着错位。
  补偿量抽成 `karaokeCenterDx()` 纯函数并留了一条实测用例，防止将来有人把它当冗余删掉。

> 推广：**跨渲染路径的样式不能靠「我设了」来判断生效**。同一段文字经 `Text` 和经
> `TextPainter` 自绘，对齐行为就不一样；这类差异只能用量测（探针测试）确认，
> 猜一定会猜错。
