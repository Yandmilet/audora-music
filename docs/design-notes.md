# 设计要点

> 本文由原 README「设计要点」「关于登录后能否取消限流」章节迁出。
> 编号与原 README 保持一致，便于历史讨论对照。

### 1. 界面语言参考千千音乐

- 品牌色 `#E5484D`，中性灰底 `#F5F6F8`
- 大圆角（卡片 18px，胶囊 999px）
- 深色模式通过语义令牌整体切换，而非逐处硬编码

### 2. 音源状态在 UI 中可见

每首歌都带状态徽章：

| 徽章     | 含义                        |
| ------ | ------------------------- |
| 已匹配（绿） | 匹配分 ≥ 0.82，自动采用           |
| 待确认（橙） | 匹配分在 0.62 ~ 0.82 灰区，需人工复核 |
| 无音源（灰） | 未找到候选，需手动指定               |

「我的 → 音源匹配管理」集中处理待确认项，支持查看 bvid / 音质 / 匹配分 / 时长校验 / UP主。

### 3. 同名异曲的直观演示

搜索「起风了」会同时出现：

- 买辣椒也用券 版 → **已匹配**
- 吴青峰 版 → **待确认**（时长差 -36 秒，翻唱/现场版）

这正是匹配算法要解决的核心问题在 UI 层的体现。

### 4. 空态优先于假数据

**库为空时显示空状态，不填演示数据。**

早期版本在空库时塞 30 首 mock 歌，看起来「功能齐全」，实际后果是：

- 用户分不清「已经导入成功了」还是「看到的还是假的」
- 导入真歌之后 UI 毫无变化 → **无法验证任何一条链路是否真的通了**
- 这类缺陷没有任何异常可抓，测试也只能断言行为

所以 `repo == null` 是**唯一**允许 mock 的入口（单测 / 纯 UI 预览），
真实运行时（`repo != null`）库为空就老老实实显示「还没有歌，去导入」。
契约细节见[架构与数据流 → 空态契约](architecture.md#空态契约重要别改回去)，由 `test/empty_library_test.dart` 锁死。

### 5. 一条 `songMid` 贯穿全链路

领域模型 `Song` **刻意不含** `songMid` / `albumMid` 这类存储字段——
它是播放器视角的「一首歌」，不该知道 QQ音乐的主键长什么样。

但这带来一个隐蔽的架构陷阱：**只要 `Song` 单独跨过一次边界，mid 就丢了**，
下游只能 `local:title|artist` 派生，而 `fetchLyric` 见到 `local:` 前缀直接返回 `null`
→ 歌词静默失效、零报错（E23）。

修法不是「在 `Song` 上加字段」（那会污染领域模型），而是**让 mid 明确地跟着走**：

| 边界      | 承载类型            | 作用                                    |
| ------- | --------------- | ------------------------------------- |
| 搜索 → UI | `ResolvedEntry` | 带着 mid 出 provider                     |
| UI → 入库 | `OnlineSong`    | 让 `importOnline` 在**类型层面**就必须拿到真实 mid |

> 教训：`importOnline(List<Song>)` 这种签名是错的——它能编译、
> 能跑通、接口全绿，只是歌词永远空白。

### 6. 收藏与播放统计独立建表

`liked_song` / `play_log` / `play_stat` 三张表**不复用 `song` 的列**，理由是：

- **收藏是用户行为，不是歌的属性**。导入走 `upsert`（`ON CONFLICT DO UPDATE`），
  若 `liked` 是 `song` 上的列，重导一次同一首歌就会把用户的红心悄悄抹掉。
- 收藏用 `INSERT OR IGNORE` 而非 `REPLACE`——`REPLACE` 会重置 `liked_at`，
  让「最近收藏」的排序在每次重复点击时乱跳。
- **流水与聚合分开**：`play_log` 是事件流（无上限，喂「最近播放」），
  `play_stat` 是聚合（每歌一行，喂「常听」）。裁流水不影响统计，
  反过来也不用为了「最近播放」去扫全量聚合表。

配套的两条门限：

- **满 30 秒才计数**（`PlayStatsDao.countingThresholdMs`）。否则「常听」
  退化成「我最近点开过什么」，前奏都没听完的歌也上榜。
- **只累计 0 < Δ ≤ 2 秒的位置增量**，其余视为 seek / 跳变，不计入收听时长。

### 7. 音质偏好是上限，不是强制

设置里的「音质偏好」传给拉流层的是一根**天花板**（`qualityCeiling`），
而不是「必须给我这个档」：

```
用户选 192K →  ceilings = 192K
   ├─ B站该视频有 192K  → 用 192K
   ├─ 只有 132K / 64K   → 放宽，拿最高可用档（别静默无声）
   └─ 没有任何 audio 流 → 返回 null，走原有的失效重匹配
```

**宁可音质差一点，也不要因为「用户偏好的档位不存在」就放不出声。**
这是唯一合理的降级方向：音质是可感知的取舍，无声是功能不可用。

### 8. 匹配速度由「请求数」决定，而请求数由 `enrichTopK` 决定

音源来自 B站，受**全局限流 30 次/分钟**约束（`BiliApiClient` 与 `MatchEngine`
**共用同一个** `RateLimiter`，分开算额度等于没限流）。所以：

```
单首歌请求数 = Stage1 搜索路数(4) + Stage3 详情候选数
等待时间     = 请求数 ÷ 30 × 60 秒
```

Stage 3 曾对**整个候选池**逐条查详情（`maxCandidates = 30`）：
4 + 30 = **34 次 ≈ 68 秒/首**，导入 20 首要等 20 分钟以上 ——
而最终只有 1 条胜出，另外 29 次请求是纯浪费。这是「匹配好慢」的根因。

现在的做法是**预筛**（`MatchEngine._preselect`）：先用搜索阶段已有的字段
跑一次粗排，只把 Top-`enrichTopK` 送进详情接口。

> 为什么粗排是可靠的：六维里权重最高的标题(0.30)与时长(0.30)
> **搜索接口就已经给全了**；详情补的分区(0.08)与文本规范度(0.07) 合计仅 0.15，
> 且缺失时对所有候选是**同向**影响，不改变相对次序。再加上 Stage 2 的
> ±30 秒时长粗筛**已经**在搜索时长上执行过，排错序的空间被限制在 30 秒以内。

效果：详情 **30 → 6**，总请求 **34 → 10**，单首 ≈68 秒 → **≈20 秒（3.4×）**。

同时 `maxCandidates` 放宽到 60 —— 候选池只做本地计算（硬过滤 + 预筛），
网络开销由 `enrichTopK` 控制，所以池子放大是**纯准确率收益**。

**⚠️ 两条不能动的护栏**（都由 `test/match_pipeline_test.dart` 锁死）：

1. **详情请求数必须被 `enrichTopK` 兜住**。删掉预筛，速度立刻打回 68 秒/首。
2. **预筛只能按打分排序，不能按播放量**。设计文档自己说「播放量高的往往是
   翻唱或鬼畜，热度与正确性不相关」——按错信号排序既慢又漏。
   （测试专门造了「正确音源播放量最低」的池子来验证它仍能胜出。）

另外 `_recall` 的「分档搜索为空 → 回退全量」**只允许做一次**：递归进去后
`durationFilter` 会重算出同一个值、查询词也相同，无结果时会变成
「空 → 递归 → 还是空 → 再递归」的**无限循环**，每轮白烧 8 次配额且永不返回，
把串行的批量匹配队列**永久堵死**（不报错，只是卡住）。

### 9. 分钟级的操作必须可预期、可中止

匹配受限流约束，批量导入几十首时**必然**要等几分钟。能做的不该是假装它很快，
而是让它可预期：

- **进度 + 剩余时间**：只转圈会让用户以为卡死。ETA 按「已用时 ÷ 已完成数」
  外推，但**首首完成前不给估计** —— 样本为 0 时任何外推都是编的。
- **两处渲染**：能触发操作的地方给完整卡片（进度条 / 当前歌 / 中止），
  外壳层给一条极薄的状态条 —— 用户等一会儿就会切 tab 去干别的，
  进度只在一个页面里可见等于切走就失联。
- **可中止**：分钟级操作不让取消，用户下错命令后只能干等，那比慢本身更糟。

### 10. 按需匹配优先于批量预处理（用户等的时间 ≠ 任务总时长）

这是本项目**投入产出比最高**的一次优化，值得单独记一笔。

限流是硬约束：全局限流 30 次/分钟，单首约 10 次请求，20 首就要 6~7 分钟。
看起来「只能忍」，但其实**用户等的不是那 7 分钟，而是「第一首能播」那一刻**。

原先的链路是**串行依赖**：

```
导入 N 首 → 全部匹配完 → 才能播第一首        用户等的 = 任务总时长 = 6~7 分钟
```

而用户真正会听的往往只有导入的其中几首。改成按需之后：

```
导入 N 首（秒级，元数据来自 QQ音乐，不需要 B站）
  → 点第 1 首 → 只匹配这一首（~20 秒）→ 开始播     用户等的 = 20 秒
  → 点第 2 首 → 只匹配这一首（~20 秒）
```

**首首可播时间从 6~7 分钟压到约 20 秒**，而且**总请求量更少** ——
不听的歌根本不会被匹配，不消耗任何限流配额。批量匹配没有消失，
它降级成「我就是要全部提前备好」的预处理手段。

配套的两个细节，都是**不报错、只是不对**的失败模式：

1. **队列必须就地替换对象。** `matchOne` 只写数据库，不改内存里的 `Song`。
   不做同步的话，播放页的音源徽标会一直显示「无音源」（可歌已经能播了），
   而且下一首续播拿到的还是旧对象 → 再白等 20 秒重新匹配一次。
2. **已经有音源的歌必须短路。** 否则每次播放都白烧 10 次请求的配额，
   速度会莫名其妙地掉回去。

两条都由 `test/on_demand_match_test.dart` 锁死 —— 它们都**不抛异常**，
只能靠「请求次数」和「对象是否是新的」这类行为断言抓住。

### 11. 点播场景：宁播最相似候选，也不静默失败

真机实测撞出来的。点榜单第一首（2026-09-25 发行的新歌），等了 30 秒
**没有任何反应**——数据库里匹配其实跑完了：找到 5 个候选，最高分 0.810，
但 AUTO 阈值是 0.82，全部被标成 REVIEW 存起来不激活。播放链路一看
「没有激活音源」→ 报错 → 而错误只显示在播放页里，用户在浏览列表里
看到的就是「点了没反应」。

B站对新歌/冷门歌常常只有非标准标题的投稿，最高分卡在 0.81 是常态。
按 AUTO 硬卡，**浏览优先的产品形态下大量歌都会「点了没反应」**。

处理方式是**分语境**：

| 场景                           | 激活策略                                | 理由                                          |
| ---------------------------- | ----------------------------------- | ------------------------------------------- |
| 批量预处理（`matchAllUnmatched`）   | 只激活 AUTO（≥0.82）                     | 无人监督地给全库激活低置信候选，会大面积播到翻唱                    |
| 用户点播（`ensurePlayableSource`） | REVIEW 里 ≥0.60 的最高分候选也激活，并 toast 告知 | 用户明确想听这一首；播一个可能不太对的版本 + 一句「可去匹配管理更换」，好过静默失败 |

红线不破：激活仍走 `BindingDao.activate`（唯一激活在事务内保证，
由 `test/online_play_test.dart` 锁死）。0.60 底线之下不播——
低于它的候选大概率根本不是这首歌。

同一个错误的另一个教训：**点歌失败的提示必须全局可见**。
`playbackError` 只在播放页渲染，而点歌的人往往还没打开播放页。
现在 AppState 提供全局 `toast`（5 秒自动消失），外壳层渲染，
与匹配进度条同一插槽。

## 关于「登录后能否取消限流」

结论：**不能，而且方向是反的。** 这里记下依据，免得以后反复讨论。

- **`-412` 是 IP 维度的拦截**，不是「你没登录」。B站 官方错误码表里
  `-412` 的说明是 *Risk Control / Request intercepted (IP blocked)*；
  频率那条是 `-799 Too frequent`。换 Cookie 换不掉 IP。
- **登录会放大风险，不是降低。** 匿名被风控 = 出口 IP 被临时拦（等几分钟）；
  登录态被风控 = 关联到**你的账号**（错误码表里有 `-102 账号封禁`）。
  拿账号去换速度是净亏损。
- **登录真正的收益是音质，不是速度。** 搜索 / 详情 / 匹配整条链路只需要
  `buvid3` 这类**匿名指纹 Cookie**，而这些可以自动获取
  （见 `bili_cookie_session.dart` 的 `_anonymousCookies()`）。
  登录换来的是 `30280`（192K）及以上档位的可用性。
- 登录入口已经现成：`BiliCookieSession.setUserSession(sessdata: ...)`。
  缺的只是「扫码换 SESSDATA」那一步 passport 流程，以及**失效降级** ——
  SESSDATA 会过期、也会在别处登录时被服务端主动踢掉，
  处理不好会让匹配从「慢」变成「全失败」。

真正让「感觉慢」消失的是架构改动（见设计要点 10），不是提高限流上限。
**放宽限流是拿风控换速度**：一旦触发 `-412`，后果是匹配整体失败，比慢更糟。
